# Skills

A curated collection of agent skills for Claude Code.

## Setup (run once after cloning)

```bash
git clone git@github.com:DMGiulioRomano/skills.git
cd skills
./install.sh
```

`install.sh` does two things:
1. Creates symlinks from `~/.claude/` to the **core** skills (`core.txt`) **and** the deliberate config files in this repo
2. Installs `post-merge` and `post-checkout` git hooks so symlinks stay in sync automatically on every `git pull` or branch switch

## Core vs vault

Only the skills listed in `core.txt` are linked into `~/.claude/skills/`. Every
other skill stays in the **vault** and is invisible to Claude until activated.

The point is not saving tokens — the whole vault costs ~3k of a 1M context.
It's **precision**: thirty skill descriptions competing to trigger is a
worse signal than eight. When one fires, it should be because it belongs.

```bash
./link-skill.sh -l              # what's in the vault, what's active
./link-skill.sh humanizer       # activate — usable immediately, no restart
./link-skill.sh -r humanizer    # back to the vault
./sync-links.sh --prune         # one-off: unlink everything not in core.txt
```

Activation is **hot**: a newly linked skill is invocable in the running
session. A plain `sync-links.sh` never deactivates a skill you linked on
purpose — only `--prune` does, and that's for the one-time migration.

Claude reaches for the vault on its own: the `skill-on-demand` rule tells it to
read `CATALOG.md` when a task looks covered by something not currently loaded,
and to propose activating it. The catalog is read on demand, never held in
context.

## Catalog

**[CATALOG.md](CATALOG.md)** — every skill in the vault with its description.
Generated by `./gen-catalog.sh` from the `SKILL.md` frontmatters; regenerate it
after adding, removing, or updating a skill. Don't edit it by hand and don't
duplicate the list here — a hand-kept list drifts on the first `update-skill.sh`.

## Config propagation (CLAUDE.md + rules)

Besides skills, the repo is the single source of truth for the **deliberate**
config layer, propagated by the same symlink mechanism:

- `.claude/CLAUDE.md` → `~/.claude/CLAUDE.md` (global default for every repo)
- `.claude/rules/*.md` → `~/.claude/rules/*.md` (modular, machine-wide workflow rules)

Notes:
- Rules are symlinked **per-file**, so machine-local rules dropped into
  `~/.claude/rules/` keep working alongside the synced ones.
- If a **real** (non-symlink) `~/.claude/CLAUDE.md` already exists, it's moved to
  `CLAUDE.md.bak` before the symlink is created — no local config is destroyed.
- The **auto memory** (`MEMORY.md`) is intentionally **not** synced: it's local
  to each machine and meant to be regenerated, not shared.
- `CLAUDE.md`/rules are context, not enforcement: they steer behavior but don't
  block actions. For a hard guarantee (e.g. tests green before a commit) use a
  `PreToolUse` hook or a git `pre-commit` hook — out of scope here.

## How It Works

Skills are loaded by Claude Code from `~/.claude/skills/`. Core skills are
symlinked there permanently, vault skills on demand — either way the repo stays
the single source of truth across all your machines.

Add an alias to your `.zshrc` (or `.bashrc`) if you want skills loaded via `--add-dir` instead of symlinks:

```bash
alias claude="claude --add-dir /path/to/this/repo"
```

> The directory structure must place skill files inside `.claude/skills/` within the repo root — that's the path Claude Code expects when resolving skills from an external directory.
